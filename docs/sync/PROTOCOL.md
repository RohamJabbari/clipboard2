# Clipboard2 Sync Protocol v1

The contract between the Mac app, the Windows app and `clipboard2-api`. Everything a user syncs is
encrypted on the device; the server stores ciphertext plus the metadata listed under
[What the server sees](#what-the-server-sees). Byte-exact behaviour is pinned by
[`test-vectors.json`](test-vectors.json) (generated by `server/scripts/vectors.ts`); both clients
must pass every vector.

Accounts live in `clipboard2-db` itself. **The password never leaves the device**, and there is **no
password recovery**: a forgotten password means the synced data is gone. Both apps say so at sign-up.
Since 1.13 the Mac can also make **passwordless** accounts (new devices are approved by existing
ones, and recovery goes through contacts): see [Passwordless](#passwordless) and
[`docs/features/passwordless.md`](../features/passwordless.md). Windows keeps using password accounts.

## Conventions

- **Bytes in JSON** are standard base64 with padding.
- **IDs** (`uid`, space, item and blob ids) are UUIDs in lowercase hyphenated form. Swift's `uuidString` is uppercase, so lowercase it before use.
- **Invite ids** are lowercase hex.
- **Times** are Unix milliseconds as JSON integers.
- **Strings** are UTF-8 everywhere.
- **Passwords** are Unicode-NFC-normalised before key derivation.
- **Emails** are trimmed and lowercased by the client before every use. The server does the same.
- **`‖`** means concatenation.

## Cryptography

### Primitives

| Name | Definition |
|---|---|
| `AEAD(key, plaintext, aad)` | AES-256-GCM with a random 12-byte nonce. Output `0x01 ‖ nonce(12) ‖ ciphertext ‖ tag(16)`. Decryption rejects any other version byte. |
| `HKDF(ikm, salt, info)` | HKDF-SHA256 with 32 bytes of output. An empty salt is zero-length: CryptoKit `Data()`, .NET `[]`. |
| `PBKDF2(password, salt, iterations)` | PBKDF2-HMAC-SHA256 over `NFC(password)` as UTF-8, 32-byte output. New accounts use **600 000** iterations and a random 16-byte salt. |
| P-256 public key | X9.63 uncompressed, 65 bytes: `0x04 ‖ X ‖ Y`. |
| P-256 private key | Raw scalar, 32 bytes (CryptoKit `rawRepresentation`, .NET `ECParameters.D`). |
| `ECDH(priv, pub)` | The raw 32-byte X coordinate of the shared point. |

### Password-derived keys

```
master   = PBKDF2(password, kdfSalt, iterations)
authKey  = HKDF(master, "", "clipboard2 auth")   sent to the server to log in, never stored by the client
wrapKey  = HKDF(master, "", "clipboard2 wrap")   never leaves the device
```

The server stores only `scrypt(authKey)`, so its database can't be used to derive `wrapKey`.

### Account and space keys

```
AK          = random(32)                                   account key, one per user
wrappedAK   = AEAD(wrapKey, AK, "c2/ak/v1/" + uid)
idPriv      = random P-256 key; idPub = its public key
wrappedPriv = AEAD(AK, idPriv, "c2/priv/v1/" + uid)

SK          = random(32)                                   one per space (personal and each group)
wrapSpaceKey(SK, spaceId, memberUid, memberPub):
    eph       = fresh P-256 key
    wk        = HKDF(ECDH(eph.priv, memberPub), eph.pub ‖ memberPub, "c2/space/v1/" + spaceId)
    wrapped   = eph.pub(65) ‖ AEAD(wk, SK, "c2/space/v1/" + spaceId + "/" + memberUid)
unwrap: split off the first 65 bytes as eph.pub, then wk = HKDF(ECDH(idPriv, eph.pub), eph.pub ‖ idPub, …)

itemKey     = HKDF(SK, "", "c2/item/v1")
nameKey     = HKDF(SK, "", "c2/name/v1")
item        = AEAD(itemKey, payloadJSON, "c2/item/v1/" + spaceId + "/" + itemId + "/" + category)
blob        = AEAD(itemKey, bytes,       "c2/blob/v1/" + spaceId + "/" + blobId)
groupName   = AEAD(nameKey, utf8(name),  "c2/name/v1/" + spaceId)
```

The client generates `uid` (a random UUID) at sign-up because it's part of the AAD.

### Invite codes

```
codeBytes = random(16)                                     128 bits
code      = base32(codeBytes)                              RFC 4648 alphabet A–Z 2–7, no padding: 26 characters,
                                                           shown as 4-character groups joined by "-"
                                                           (XXXX-XXXX-XXXX-XXXX-XXXX-XXXX-XX)
inviteId  = hex(SHA-256(codeBytes))                        64 lowercase hex chars; the server only ever sees this
inviteKey = HKDF(codeBytes, "", "clipboard2 invite")
sealedKey = AEAD(inviteKey, SK, "c2/invite/v1/" + spaceId)
```

**Parsing a typed code:**
1. Remove spaces and `-`, then uppercase.
2. Map `0`→`O`, `1`→`I` and `8`→`B`, to forgive misreadings.
3. Require exactly 26 characters and base32-decode them to 16 bytes. The last 2 bits must be zero.

### Sign-up codes

Sign-up is invite-only. A **sign-up code** is made by the server (`POST /v1/signup-codes`), not the
client, and isn't key material:

```
code       = 80 random bits in the invite-code alphabet: 16 characters,
             shown as 4 groups of 4 joined by "-" (XXXX-XXXX-XXXX-XXXX)
normalised = the typed code with spaces and "-" removed, uppercased, 0→O, 1→I, 8→B; exactly 16 characters
stored     = SHA-256(utf8(normalised))                     the server keeps only this
```

The app's "Invite code" field takes either kind: 16 characters after normalising is a sign-up code
(sent as typed, as `signupCode`), 26 is a group invite code (sent as `groupInviteId` = its `inviteId`,
and joined right after the account exists).

### Known v1 limits
- Removing a member doesn't rotate the space key. Their access ends because the server refuses them, not because of crypto.
- Emails are verified only through Continue with Google (or, once mail sending exists, an emailed code). An unverified address can be taken over by a later verified claim; see [Emails](#emails).

## Item payloads

The plaintext inside `item` is one compact JSON object. Readers ignore unknown fields; writers omit nulls.

```jsonc
// type "clip"
{"v":1,"type":"clip","kind":"text|richText|image|file","text":"…","preview":"…",
 "rtf":"<b64>","html":"<b64>","files":["file:///…"],"fileBlobs":[{"name":"Report.pdf","blob":"<blob uuid>","size":0}],
 "imageBlob":"<blob uuid>","thumbBlob":"<blob uuid>","imageWidth":0,"imageHeight":0,"byteCount":0,
 "sourceId":"com.apple.Safari","sourceName":"Safari",
 "isPinned":false,"pinnedAt":null,"label":null,"copyCount":1,
 "createdAt":0,"lastCopiedAt":0,"contentHash":"text:…","folder":"<folder item id>"}
// type "folder"
{"v":1,"type":"folder","name":"…","label":null,"parent":"<folder item id>","createdAt":0,"updatedAt":0}
// type "snippet"
{"v":1,"type":"snippet","name":"…","keyword":"…","body":"…","createdAt":0,"updatedAt":0}
// type "secret"
{"v":1,"type":"secret","name":"…","value":"…","createdAt":0,"folder":"<folder item id>",
 "username":"me@example.com","urls":["https://accounts.google.com","youtube.com"],"notes":"…",
 "origin":"<origin item id>"}
// type "otp" (category "otp", only in authenticator spaces; never sent to anyone but the owner)
{"v":1,"type":"otp","issuer":"GitHub","account":"me@example.com","secret":"<base32, no padding>",
 "algorithm":"SHA1|SHA256|SHA512","digits":6,"period":30,"createdAt":0,"updatedAt":0,
 "urls":["github.com"],"origin":"<origin item id>"}
// type "origin" (category "origin", only in the personal space)
{"v":1,"type":"origin","name":"Google","domains":["google.com","accounts.google.com"],
 "icon":"favicon:<host>|letter|symbol:<SF Symbol>|emoji:<text>",
 "notes":[{"id":"<uuid>","text":"…","createdAt":0,"updatedAt":0}],
 "documents":[{"id":"<blob uuid>","name":"Contract.pdf","size":0,"addedAt":0}],
 "entries":["shared:<authenticator space id>","secret:<secret item id>"],
 "createdAt":0,"updatedAt":0}
```

- **Passwords (1.11+):** a password is a `secret` with a site or a username. All three fields are optional and omitted when empty, so plain secrets keep their bytes and fingerprints:
  - `username`: string, trimmed.
  - `urls`: the sites, as typed or imported (a full URL or a bare host), trimmed, empty ones and case-insensitive duplicates dropped, order kept. The first one picks the password's source in Auth (its registrable domain).
  - `notes`: free text.
- **Authenticator sites (1.11+):** `urls` on `otp`, same rules; set with Edit → Website. Optional, omitted when empty.
- **Origins (1.13+, Mac):** see [Origins](#origins). `origin` on `secret` and `otp` is the lowercase id of the `origin` item the entry is filed under; omitted when unset, so other payloads keep their bytes and fingerprints.
- These fields are content: they're part of the fingerprint like every other field.
- **Unknown fields:** readers ignore them, but a client that rewrites a payload must keep the fields it doesn't know. Clients up to 1.10 (Mac) and 1.10.1 (Windows) rebuild the payload from the fields they know, so editing a password there wipes its `username`, `urls` and `notes` (and an authenticator's `urls`).
  - **Windows ≥ 1.10.2 preserves unknown fields** of every payload type (`clip`, `folder`, `snippet`, `secret`, `otp`): every top-level field it doesn't write itself (except the per-write `rev`, `toDevice`, `fromDevice`) is kept with the item — a secret's in Credential Manager next to its value, an authenticator's in its protected entry, the rest in the local database — and merged back into every payload it pushes. An unchanged item renders to the same canonical JSON (and fingerprint) as received, so it's never pushed back. Secrets and authenticators synced by an older Windows lost theirs on the way in; on upgrade they're applied once more from the server, which restores them without a push.

- **Images:** the PNG and its thumbnail are uploaded as two encrypted blobs. Their ids are listed in the payload and in `blobIds`.
- **Rich text that won't fit:** if `rtf` + `html` push the ciphertext past the item limit, drop them and sync the item as `text`.
- **Files:** each regular file of up to 100 MiB sealed, at most 10 per item, is uploaded as an encrypted blob, like images. A folder counts as one file: it is uploaded as a zip of its contents (paths relative to the folder, `/` separators, UTF-8 names with the UTF-8 flag, regular files and folders only, no symlinks), listed as `{"name":"<folder>.zip",…,"folder":true}`; `folder` is omitted for plain files. Receivers that understand `folder` unpack it to `Synced Files/<item id>/<folder>` — refusing absolute or `..` paths, dropping symlinks, and keeping it as the `.zip` when refused — while older ones just save the zip. `fileBlobs` lists them in upload order (`name` is the last path component, `size` the plaintext bytes) and `blobIds` repeats their ids. Receivers save them as `Synced Files/<item id>/<name>` — after stripping any path from `name` — and keep the item a file clip pointing there, so pasting puts real files on the clipboard. Files without a blob (too large, or from a sender without `fileBlobs`) arrive as their names, as text. Deleting the item deletes its folder.

| Category | Payload | `sortAt` |
|---|---|---|
| `history` | clip with `isPinned: false` | `lastCopiedAt` |
| `pinned` | clip with `isPinned: true` | `lastCopiedAt` |
| `snippet` | snippet | `updatedAt` |
| `secret` | secret | `createdAt` |
| `folder` | folder | `createdAt` |
| `otp` | otp | `createdAt` |
| `origin` | origin | `createdAt` |

Pinning or unpinning changes the category, and the category is part of the AAD, so the client re-encrypts and `PUT`s again.

**Folders** group saved clips within one space (personal or group; not contacts in v1). A folder may sit in another folder of the same space (`parent`, omitted at the top level); an unknown parent, a cycle or more than 8 levels reads as top level. Deleting a folder moves its clips and subfolders to its parent.
- A clip in a folder has `isPinned: true` and `folder` set to the folder item's id; it travels as `pinned`. Clearing `isPinned` clears `folder`.
- A `folder` id the reader doesn't have (deleted, or not pulled yet) means the clip sits at the root of Saved.
- Deleting a folder deletes only the folder: each member's client moves its clips to the root lazily (they already read as root, above), and the device that deleted it re-pushes its clips without `folder`.
- Clients before 1.6 skip the `folder` category and drop the unknown `folder` field when they re-push a clip, which moves it to the root.

### Origins

An **origin** is a site in Auth edited by hand (docs/features/auth-autofill.md → Origins): a name, its
websites, an icon, notes and documents. Mac 1.13+ only; Windows doesn't show them yet.

- **Where:** category `origin`, in the **personal space only**. The server refuses it elsewhere (`400 invalid`), and older servers refuse the category altogether (`400 invalid`): the client keeps the origin locally and retries once it changes, like any refused item.
- **Fields:** `name` (may be empty when `domains` isn't); `domains`: sites as typed (hosts or URLs), trimmed, empty ones and case-insensitive duplicates dropped; every registrable domain among them is the origin's. `icon`: omitted means the first domain's favicon. `notes`: free text, in order. `entries`: see below. Empty arrays and a default icon are omitted.
- **Documents:** each `documents[i].id` is also the id of an encrypted blob of the item (`blob = AEAD(itemKey, bytes, "c2/blob/v1/" + spaceId + "/" + id)`, like a clip's files), and the item's `blobIds` lists exactly those ids. At most 12 per origin (the `blobIds` limit), each at most 95 MB plaintext. A document is never re-pointed: moving one to another origin (a merge) gives it a new id and uploads it again, so deleting the old origin (which deletes its blobs) can't take it away. Readers download each blob they don't have before applying the item; one the server no longer has (`404`) is dropped from the list.
- **Filing entries under an origin**, first match wins:
  1. the entry's own `origin` (on `secret` and `otp`), when that origin exists;
  2. an origin whose `entries` lists it: `shared:<space id>` for an authenticator shared with you, `secret:<id>` for someone else's secret in a group (entries you can't rewrite);
  3. an origin claiming one of the entry's sites' registrable domains (several origins claiming one: the oldest by `createdAt`, then id);
  4. for an authenticator grouped by its issuer, an origin with that name (case-insensitive, trimmed);
  5. otherwise automatic grouping by site, as before.
  An `origin` naming an origin this device doesn't have (deleted, not synced yet, or someone else's in a group) is ignored.
- **Older clients:** they skip the unknown category (Mac ≤ 1.12 and Windows ignore items whose type they don't know, and never record them, so they never delete them). `origin` on `secret`/`otp` is an unknown field to them: Windows ≥ 1.10.2 keeps it; Mac ≤ 1.12 drops it when it rewrites the entry (an edit there), after which the entry is filed by its domains again (rules 3–5).

## API

- Bodies are JSON.
- Every route except `/v1/auth/prelogin`, `/v1/auth/signup` and `/v1/auth/login` needs `Authorization: Bearer <session token>`.

**Errors** are `{"error": "<code>", "message": "…"}`:

| Code | Status |
|---|---|
| `unauthenticated` | 401: missing, unknown, revoked or expired session |
| `invalid_credentials` | 401 |
| `forbidden` | 403 |
| `send_not_allowed` | 403: the caller lacks [Send](#member-access) in this group |
| `invite_required` | 403: sign-up without `signupCode` or `groupInviteId` |
| `invite_invalid` | 403: that sign-up code or group invite is unknown, used or expired |
| `not_found` | 404 |
| `no_account` | 404 |
| `conflict` | 409 |
| `username_taken` | 409 |
| `invalid` | 400 |
| `clock_skew` | 400: an item time is more than 10 minutes ahead of the server's clock |
| `too_large` | 413 |
| `quota_exceeded` | 403 for per-user and per-space limits; 413 with `"scope": "group"` or `"scope": "server"` for group and server storage (see [Limits](#limits)) |
| `rate_limited` | 429, with `Retry-After` in seconds and `retryAfter` in the body |
| `too_many_codes` | 429: already 10 open sign-up codes |
| `feature_disabled` | 403: email codes or the email recovery method while `FEATURE_EMAIL_CODES` is off, or Google sign-in on a server without it |
| `invalid_token` | 401: a Google ID token that didn't verify or was already used |
| `number_mismatch` | 409: the approver picked the wrong number; the request or recovery is closed |
| `request_closed` | 409: that request or recovery was already answered, or expired |
| `password_devices` | 409: retiring the password while other password sessions are signed in (`devices` lists them) |
| `code_invalid` | 400: a wrong or expired email code |

### Auth and sessions

| Request | Response |
|---|---|
| `POST /v1/auth/prelogin` `{email}` | `{kdf: {alg: "pbkdf2-sha256", salt, iterations}}`. Unknown emails get a deterministic fake salt (`HMAC-SHA256(serverKey, email)[0..16]`, 600 000 iterations), so this can't be used to find accounts. |
| `POST /v1/auth/signup` `{email, authKey, kdf: {salt, iterations}, uid, wrappedAccountKey, publicKey, wrappedPrivateKey, personalSpace: {id, wrappedKey}, deviceName?, username?, signupCode?, groupInviteId?}` | `201 Session`; `403 invite_required` without either invite, `403 invite_invalid` if it's unknown, used or expired; `409 conflict` if the email is taken, `409 username_taken` if the username is |
| `POST /v1/auth/login` `{email, authKey, deviceName?, platform?}` | `200 Session`; `401 invalid_credentials` (also for accounts without a password) |
| `POST /v1/auth/logout` | `204`, revokes the calling session |
| `PUT /v1/account/password` `{authKey, newAuthKey, kdf: {salt, iterations}, wrappedAccountKey}` | `204`. Checks the current `authKey`, replaces the password verifier and `wrappedAK` (AK itself doesn't change), and revokes every other session. |
| `GET /v1/account` | `Account` |
| `PUT /v1/account/username` `{username}` | `200 {username}`; `409 username_taken` |
| `DELETE /v1/account` `{authKey}` (password accounts) or `{confirm: "<username>"}` (passwordless accounts, from a device session) | `204`. Deletes sessions, sign-up codes, the personal space, owned groups (items, blobs, invites), memberships, and every [direct space](#contacts) they are in or were asked into (pending requests both ways), for both people. Every live item the user wrote in other people's groups becomes a `user` tombstone (its `updatedAt` raised to the deletion time, `authorUid` then `null`), and their blobs there are deleted. |
| `GET /v1/sessions` | `{sessions: [DeviceSession]}`, the caller's unexpired sessions, most recently used first. `id` is a UUID; `current` marks the calling session. |
| `PATCH /v1/sessions/:id` `{windowMs, acknowledgement?}` | `200 DeviceSession`. Device sessions only (`400 invalid` otherwise). The new expiry is now + `windowMs`, or indefinitely (`windowMs: null`, needs the [acknowledgement](#session-windows)). Another device may only shorten it (`403 forbidden`). |
| `DELETE /v1/sessions/:id` | `204`, signs that device out (it may be the calling session); `404` if it isn't one of the caller's |
| `POST /v1/signup-codes` | `201 {id, code, expiresAt}`. A new [sign-up code](#sign-up-codes), valid 14 days, single use. `code` is shown only here. `429 too_many_codes` with 10 open (unused, unexpired) codes. |
| `GET /v1/signup-codes` | `{codes: [{id, createdAt, expiresAt}]}`, the caller's open codes |
| `DELETE /v1/signup-codes/:id` | `204`, revokes an open code; `404` otherwise |

```jsonc
Session = {"token","expiresAt":null|<ms>,"account": Account}        // expiresAt null: a device session kept indefinitely
Account = {"uid","email","emailVerified","emailReleased","kdf":null|{"alg":"pbkdf2-sha256","salt","iterations"},
           "wrappedAccountKey":null|"<b64>","hasPassword","publicKey","wrappedPrivateKey","personalSpaceId",
           "username":null|"<string>"}
DeviceSession = {"id","deviceName","createdAt","lastUsedAt","current","kind":"password|device","platform":null|"macos|windows|…",
                 "windowMs":null|<ms>,"expiresAt":null|<ms>,"country":null|"AT","city":null|"Vienna"}
```

`kdf` and `wrappedAccountKey` are `null` only for passwordless accounts, which only signs in through
device sessions; password logins (and so Windows) never see them null. `emailReleased`: a verified
account took this account's unverified address; it should change its email.

- **Tokens:** 32 random bytes as base64url. The server stores only their SHA-256.
- **Expiry:** password sessions expire 30 days after their last use. Every authenticated request slides the expiry forward, at most once an hour. Device sessions (passwordless) end hard at their [window](#session-windows) and never slide.
- **On the device:** the token, uid, email, AK and idPriv go in the Keychain (Mac, service `<bundle id>.sync`) or Credential Manager (Windows, `Clipboard2/sync/*`), never in settings files.
- **Session ended:** on `401 unauthenticated` the client asks for the password again (prelogin, then login), unlocks AK from the fresh `Account`, and carries on.
- **Signup:** `kdf.iterations` must be at least 100 000.
- **Usernames:** optional; trimmed and NFC-normalized, then 3–24 Unicode letters, digits, `_`, `.` or `-`, starting with a letter or digit (`invalid` otherwise). Stored as typed, unique case-insensitively. Accounts without one have `username: null`.
- **Sign-up invites:** `signupCode` (as typed; the server normalises it) is consumed by the sign-up.
  `groupInviteId` must be an unused, unexpired group invite (a contact code doesn't count); sign-up doesn't consume it, joining does.
  The invite is checked before the email, so sign-up can't be used to find accounts without one.
  New servers get their first code from `npm run signup-code` (an operator code that belongs to nobody).
- **Rate limits:** prelogin, signup and login (and the password checks of password change and account
  deletion) share one limit per IP and one per email, counted in Postgres in fixed one-minute windows,
  so they hold across instances. The client IP is the last `X-Forwarded-For` hop (Cloud Run's front
  end); earlier entries are ignored. Password hashing runs at most 2 at a time per instance with a
  short queue; beyond it the answer is `429 rate_limited` with `retryAfter`.

### Spaces and groups

**Endpoints:**

| Request | Response |
|---|---|
| `GET /v1/spaces` | `{spaces: [Space]}`, every space the caller belongs to |
| `POST /v1/groups` `{id, encryptedName, wrappedKey}` | `201 Space`. The caller becomes owner; `wrappedKey` is SK wrapped to the caller. |
| `PATCH /v1/groups/:id` `{encryptedName}` | `204`, owner only |
| `DELETE /v1/groups/:id` | `204`, owner only. Removes all items, blobs and invites. |
| `GET /v1/groups/:id/members` | `{members: [Member]}`, members only, owner first. `username` may be `null`; `name` is as in `Space.members`. No emails. |
| `PATCH /v1/groups/:id/members/:uid` `{canSend?, canSeeSecrets?}` | `200 Member`, the member as the members list shows it. Owner only (`403 forbidden`). At least one field (`400 invalid`); the owner's own row can't change (`400 invalid`); unknown member `404`. See [Member access](#member-access). |
| `DELETE /v1/groups/:id/members/:uid` | `204`. The owner can remove others; a member can remove themselves (leave). The owner can't leave and has to delete the group instead. |

```jsonc
Space = {"id","kind":"personal|group|direct|authenticator","role":"owner|member","ownerUid",
         "wrappedKey","encryptedName":null|"<b64>","memberCount",
         "members":[{"uid","name"}],"canSend","canSeeSecrets","createdAt"}
Member = {"uid","username":null|"<name>","name","role":"owner|member","canSend","canSeeSecrets"}
```

- **`members`:** everyone in the space, owner first (a personal space lists only the caller). `name` is the username, or the email's part before `@` if there is none. Clients show it next to items by matching `authorUid`.
- **`canSend`, `canSeeSecrets`:** the caller's own [access](#member-access). Only on `group` spaces; absent on the other kinds.

#### Member access

Each group member has two booleans, both `true` by default (and for everyone who joined before 1.10):

- **Send** (`canSend`): may add and change items and upload blobs.
- **Secrets** (`canSeeSecrets`): receives the group's `secret` items and may write or delete them.

The owner always has both; only the owner changes them (`PATCH /v1/groups/:id/members/:uid`). Personal,
direct and authenticator spaces ignore them. The server enforces:

| Route | Without Send | Without Secrets |
|---|---|---|
| `GET /v1/spaces/:id/changes` | unchanged | `secret` rows are left out entirely, tombstones included |
| `PUT /v1/spaces/:id/items/:itemId` | `403 send_not_allowed`, for new items and changes alike | `403 forbidden` when the body or the stored item (tombstones included) is `secret` |
| `DELETE /v1/spaces/:id/items/:itemId` | allowed (the usual author/owner rule) | `403 forbidden` for a `secret` item, tombstones included |
| `POST /v1/spaces/:id/blobs` | `403 send_not_allowed` | unchanged |

`send_not_allowed` is checked before `forbidden`. When Secrets is turned back on, rows the feed skipped
are behind the client's cursor, so the client resets that space's cursor to `0` to fetch them.
Revoking Secrets doesn't rotate the space key: a device that already decrypted a secret could keep it.

### Invites

| Request | Response |
|---|---|
| `POST /v1/groups/:id/invites` `{inviteId, sealedKey}` | `201 {inviteId, expiresAt}`, owner only. Valid 7 days, single use. |
| `GET /v1/groups/:id/invites` | `{invites: [{inviteId, createdAt, expiresAt}]}`, owner only, pending invites only |
| `DELETE /v1/groups/:id/invites/:inviteId` | `204`, owner only, revokes the invite |
| `GET /v1/invites/:inviteId` | `{spaceId, sealedKey, encryptedName, memberCount, expiresAt}`, any signed-in user; `404` if unknown, used or expired |
| `POST /v1/invites/:inviteId/accept` `{wrappedKey}` | `201 Space`. Joins as `member` and consumes the invite. `wrappedKey` is SK wrapped to the caller's own public key. `409` if already a member. |

**Flow:**
1. **Owner:** generates a code, uploads `{inviteId, sealedKey}`, and shows the code once, with a Copy button.
2. **Invitee:** pastes the code, then `GET /v1/invites/:inviteId`, opens `sealedKey` to get SK, decrypts `encryptedName` to show "Join ‹name›?", and on confirm calls `accept` with SK wrapped to itself.

**Rate limits:** invite fetches and accepts, user lookups and contact requests share their own limit of 20/min per user.

### Contacts

A **contact** is a `direct` space: exactly two members, no name, otherwise a normal space (same
`SK`, item and blob encryption, changes and pushes). Sending something to a contact is pushing an
item into that space. The client shows items the *other* member wrote there in its **Inbox**.

- **Listing:** `GET /v1/spaces` leaves `direct` spaces out unless the client asks with
  `?include=direct` (clients from before contacts would show them as unnamed groups). Every
  established contact (a direct space with both people in it) is listed, `kind: "direct"`, `encryptedName: null`;
  `members` names both people, so the contact's name is the member who isn't the caller.
  Pending ones (an outgoing request, an unused code) aren't listed: they're in `GET /v1/contacts/requests`
  and `GET /v1/contacts/invites`.
- **One per pair:** two people have at most one direct space, counting pending requests and
  accepted contacts, in either direction. A second request or code accept between them is `409 conflict`.
- **Either member** may delete any item in a direct space (not only its author), and either may end
  the contact.

**Two ways to add someone:**

1. **Username + accept.** The requester looks up the other person's public key, makes the space and
   wraps `SK` to both of them. The other person sees a pending request and accepts or declines. Until
   then they aren't a member: they can't read the space and nothing can be sent.
   The server enforces both: item `PUT`s and blob uploads into a direct space with only one member
   (a pending request or an unused code) answer `403 forbidden`.
2. **One-time code.** Exactly like a group invite code ([Invite codes](#invite-codes), the same
   `inviteId`/`sealedKey` derivation with `spaceId` the direct space). Whoever enters the code
   becomes the contact immediately; no accept step, since sharing the code was the consent.

| Request | Response |
|---|---|
| `GET /v1/users/:username` | `{uid, username, name, publicKey}`. Case-insensitive match. `404 not_found` if nobody has it; `400 invalid` for your own. Shares the invite rate limit (20/min per user). |
| `POST /v1/contacts/requests` `{username, spaceId, wrappedKey, recipientWrappedKey}` | `201 ContactRequest`. Creates direct space `spaceId` with the caller as owner (`wrappedKey` = SK wrapped to the caller) and stores `recipientWrappedKey` (SK wrapped to the recipient's public key, AAD with the recipient's uid) until accepted. `404` unknown username, `400 invalid` yourself, `409 conflict` already contacts or a pending request either way (or `spaceId` taken), `403 quota_exceeded` over a [limit](#contacts) (yours or the recipient's). Counts against the invite rate limit, like the lookup, since it also answers `404` for unknown usernames. |
| `GET /v1/contacts/requests` | `{incoming: [ContactRequest], outgoing: [ContactRequest]}`, pending only, newest first |
| `POST /v1/contacts/requests/:spaceId/accept` | `201 Space`. Recipient only (`404` for anyone else, or once it's gone). Adds the recipient as `member` with the stored `recipientWrappedKey`. |
| `DELETE /v1/contacts/requests/:spaceId` | `204`. Recipient declines or requester cancels; deletes the space. `404` if it isn't a pending request of the caller's. |
| `POST /v1/contacts/invites` `{spaceId, wrappedKey, inviteId, sealedKey}` | `201 {spaceId, inviteId, expiresAt}`. Creates direct space `spaceId` (caller as owner) and a single-use code invite, valid 7 days. |
| `GET /v1/contacts/invites` | `{invites: [{spaceId, inviteId, createdAt, expiresAt}]}`, the caller's open contact codes |
| `DELETE /v1/contacts/invites/:inviteId` | `204`, revokes the code and deletes its still-empty space |
| `DELETE /v1/contacts/:spaceId` | `204`. Either member ends the contact: the space, its items and blobs are deleted for both. |

```jsonc
ContactRequest = {"spaceId","uid","username":null|"<string>","name","createdAt"}
// incoming: uid/name are the requester; outgoing: the recipient
```

**Codes for direct spaces** use the normal invite routes:
- `GET /v1/invites/:inviteId` also returns `kind` (`"group"` or `"direct"`) and, for `direct`,
  `ownerName` (the code's creator) so the app can ask "Add ‹name› as a contact?". `encryptedName` is `null` there.
- `POST /v1/invites/:inviteId/accept` on a direct space: `400 invalid` for your own code, `409 conflict` if you're
  already contacts (or have a pending request) with its creator (the code stays unused), `403 quota_exceeded` if
  you're at the contact limit. Old clients that don't know `kind` would try to show
  it as a group; accepting still works.
- Group-only routes (`PATCH`/`DELETE /v1/groups/:id`, members, group invites) answer `404` for direct spaces.

**Housekeeping:** a direct space that still has one member and no pending request or live code
(declined, cancelled, expired) is deleted by the server, at the latest a day after its code expires (and never in its first day).
The server sweeps opportunistically while handling `GET /v1/spaces`, at most every 10 minutes per instance.

**Limits:** 200 contacts per user (pending requests and open codes included, both directions),
50 pending outgoing requests, 20 open contact codes. Over a limit → `403 quota_exceeded`; a request to someone who is at the contact limit is refused the same way. A direct
space has the group storage limits (2 GB, 5 000 live items) and history retention (newest 200).
Deleting an account deletes all its direct spaces.

### Authenticators

An **authenticator** (a TOTP account) is an `authenticator` space whose only member is its owner. It holds
one live item, category `otp` ([payload](#item-payloads)), which syncs to the owner's devices like any item.
**The seed never leaves the owner's devices** (or the server, sealed, as for every item). People it's shared
with never get it: the owner's devices send them **pre-computed codes**, sealed to each person.

- **Owner only:** everything. The space never has other members, so nobody else can read the item.
  It takes only `otp` items, at most one live (`400 invalid` for other categories, `403 quota_exceeded`
  for a second), and no blobs (`403 forbidden`). `otp` items go nowhere else (`400 invalid`).
- Group-only and contact routes answer `404` for authenticator spaces; authenticator routes answer `404` for other kinds.
- **Listing:** `GET /v1/spaces` leaves `authenticator` spaces out unless asked: `?include=authenticator`.
  `include` takes a comma list (`?include=direct,authenticator`).
- **Sharing needs a relationship:** a contact (an established direct space) or someone in a group with the
  owner; anyone else is `403 forbidden`. No accept step; the recipient can leave.
- **Code batches.** For each person, the owner's devices upload the codes from the current step through the
  next 24 hours. Any owner device that syncs tops a share up once fewer than 12 hours remain
  (`codesUntil - now < 12h`), and right after sharing. Each upload replaces that person's batch.
- **Removing someone** deletes their batch on the server at once; codes they already downloaded keep working
  until they run out (at most 24 hours). Clients say so when removing.
- **Transfer** is the one time the seed moves: the new owner must be able to make codes. It needs an
  existing share with them, and the old owner then becomes someone it's shared with.

```
sealedCodes = eph.pub(65) ‖ AEAD(ck, codesJSON, "c2/otpcodes/v1/" + spaceId + "/" + recipientUid)
ck          = HKDF(ECDH(eph.priv, recipientPub), eph.pub ‖ recipientPub, "c2/otpcodes/v1/" + spaceId)
codesJSON   = {"v":1,"issuer":"…","account":"…","digits":6,"period":30,
               "from":<unix seconds, start of the first step>,"codes":["123456", …]}   one per step, in order
```

| Request | Response |
|---|---|
| `GET /v1/users/id/:uid` | `{uid, username, name, publicKey}`, only for the caller's contacts and people in a group with them; otherwise `404`. Shares the invite rate limit. |
| `POST /v1/authenticators` `{id, wrappedKey}` | `201 Space`, `kind: "authenticator"`, the caller as owner. `409` if `id` is taken; `403 quota_exceeded` over the limit. |
| `DELETE /v1/authenticators/:id` | `204`, owner only. Deletes the space, its item and every share. |
| `GET /v1/authenticators/:id/shares` | `{shares: [{uid, username, name, codesUntil, createdAt}]}`, owner only; `codesUntil` is `null` for an empty share. |
| `PUT /v1/authenticators/:id/shares/:uid` `{codesUntil, sealedCodes}` | `200 {}`. Owner only. Creates the share if needed (relationship and limits checked: `403 forbidden` / `403 quota_exceeded`, `400 invalid` for yourself) and replaces the batch. `sealedCodes` at most 128 KiB; `codesUntil` (ms) at most 25 h ahead. |
| `DELETE /v1/authenticators/:id/shares/:uid` | `204`. The owner removes someone, or the recipient leaves. |
| `GET /v1/shared-codes` | `{shared: [{spaceId, ownerUid, ownerName, codesUntil, sealedCodes, updatedAt}]}`, every share to the caller. `codesUntil` and `sealedCodes` are `null` until the first batch. Clients fetch it on every sync. |
| `POST /v1/authenticators/:id/transfer` `{uid, wrappedKey}` | `204`. Owner only; `uid` must have a share (`400 invalid` otherwise). `wrappedKey` is SK wrapped to them. They become the only member and owner; their share is deleted; the old owner gets a share (empty until the new owner's devices top it up). `403 quota_exceeded` if that takes either of them over a limit. |

Changes to shares and batches notify the people involved the same way item changes do.

**Limits:** 200 authenticators owned per user, 200 shared with a user, 20 shares per authenticator.
Deleting an account deletes the authenticators it owns and the shares to it.

### Heads

A cheap "did anything change?" check, so clients can poll every few seconds and run a full sync
only when something did. Optional: a server without it answers `404` and clients fall back to
polling the full sync.

| Request | Response |
|---|---|
| `GET /v1/heads` | `{heads: {<spaceId>: <seq>}, spaces, codes, contacts, security, rev}` |
| `GET /v1/heads?wait=<s>&rev=<rev>` | The same, held open until its `rev` differs from the one given or `wait` seconds pass (capped by the server, 25 s by default). |

- **`heads`:** every space the caller is a member of (all kinds, pending contacts included), with
  the highest `seq` the caller could get from its `changes` (`0` when empty). Any write or
  tombstone moves it. Without [Secrets](#member-access), a group's `secret` rows are left out here
  too, so their writes never move a member's head. A purge can lower a head; treat any difference
  as a change.
- **`spaces`:** an opaque revision (hex) of what `GET /v1/spaces` returns: membership, kind, role,
  owner, wrapped key, encrypted name, member access, and each space's members with their role and
  `name`. Joining, leaving, a rename, a new username or an access change moves it.
- **`codes`:** an opaque revision of `GET /v1/shared-codes` (shares to the caller, their batches
  and the owner's name) and of the shares of authenticators the caller owns (a new recipient or
  another device's top-up).
- **`contacts`:** an opaque revision of `GET /v1/contacts/requests` (both directions) and the
  caller's open contact codes (`GET /v1/contacts/invites`); a code expiring moves it.
- **`security`:** an opaque revision of what [Passwordless](#passwordless) clients watch: pending
  device requests (`GET /v1/device-requests`) and recoveries of the account
  (`GET /v1/account/recoveries`), recoveries and invitations where the caller is a recovery contact,
  the account's recovery setup, and its sessions and their windows. Older clients ignore it.

- **`rev`:** one opaque revision of all of the above. **Waiting:** a client that sends the `rev`
  it last acted on gets the answer as soon as anything moves it, so changes arrive as they are
  written instead of at the next poll; it polls again right away. Any successful write wakes the
  waiting requests (across instances through Postgres `LISTEN`/`NOTIFY`), which recompute and keep
  waiting when theirs didn't move; time-based changes (an expired code) show at the end of the
  wait. Servers without `rev` answer at once; clients then poll on the cadence below.

Compare values for equality only; they carry no order and change format freely. Everything is
computed in one statement: one index probe per membership plus hashes over the caller's few
membership, share and request rows.

**Rate limit:** 90/min per session, counted apart from the 120/min per user for everything else,
so polling never starves the syncs it triggers and several devices don't add up.

**Client use (macOS):** every 2 s while the panel is open or the user was active in the last 5
minutes, otherwise every 10 s. A full sync runs when `heads`, `spaces` or `codes` differ from the
values seen at the start of the last successful sync (or at least every 5 minutes); `contacts`
alone only reloads the contact lists. That is 30 requests a minute per active device and 6 when
idle, each a few milliseconds of database time.

### Items

**Endpoints:**

| Request | Response |
|---|---|
| `GET /v1/spaces/:id/changes?since=<seq>&limit=<≤500>[&full=1]` | `{items: [Item], nextSince, hasMore, resetRequired}` |
| `PUT /v1/spaces/:id/items/:itemId` `{category, sortAt, updatedAt, ciphertext, blobIds}` | `200 {seq, trimmed: [itemId]}` or `409 {error: "conflict", current: Item}` |
| `DELETE /v1/spaces/:id/items/:itemId?updatedAt=<ms>` | `200 {seq}`, idempotent. Writes a `user` tombstone and deletes the item's blobs. Returns `409 {current}` if the live item has a newer `updatedAt`. |

**Changes:** `nextSince` is the highest `seq` returned. In a group, a caller without [Secrets](#member-access) never gets `secret` rows, tombstones included. `since=0` returns the full current state. Each item's `seq` is a server-global, strictly increasing number that is assigned again on every change.
- Within a space, `seq` order is commit order: every item write locks the space row before taking a `seq`, so a cursor never moves past a change that becomes visible later.
- The purge horizon and the page are read in one REPEATABLE READ snapshot.

**Upsert rule:** last write wins on `updatedAt`.
- The incoming version is kept when `incoming.updatedAt >= stored.updatedAt`.
- A `user` tombstone counts as a stored version.
- Every id in `blobIds` must be a blob already registered in the same space. `blobIds` holds at most 12 ids.

**Write checks** (`PUT` and `DELETE`):
- `sortAt` or `updatedAt` more than 10 minutes ahead of the server's clock → `400 clock_skew`.
- In a group, an existing item (tombstones included) may be overwritten or deleted only by its
  author (`authorUid`) or the group owner; anyone else gets `403 forbidden`. Creating new items is
  open to every member with Send. Deleting an item that is already a `user` tombstone stays an idempotent `200`.
- In a group, [member access](#member-access) applies: `403 send_not_allowed` for any `PUT` without Send,
  `403 forbidden` for a `secret` item without Secrets.
- The writer becomes the item's `authorUid`.

```jsonc
Item = {"id","category":"history|pinned|snippet|secret|folder|otp|origin","seq","sortAt","updatedAt",
        "deleted":null|"user"|"trimmed","ciphertext":null|"<b64>","blobIds":[],"authorUid"}
```

**Retention:**
- `pinned`, `snippet`, `secret`, `folder`, `otp` and `origin` items stay until deleted.
- After any `history` upsert, the server keeps the newest **200** `history` items in that space by `sortAt`, ties broken by `id`. All others become `trimmed` tombstones, their blobs are deleted, and the `PUT` response lists them.
- Tombstones are kept for **90 days**. A `since` older than the space's purge horizon returns `{resetRequired: true}`, and the client re-syncs from `since=0`. While re-walking from 0, the client sends `full=1` so pages below the horizon don't ask for another reset.

### Blobs

| Request | Response |
|---|---|
| `POST /v1/spaces/:id/blobs` `{id, size, ifGenerationMatch?}` | `{url, method: "PUT", headers, expiresAt}`. Registers the blob and checks quota. Upload the ciphertext with exactly those headers; they include `x-goog-content-length-range`. |
| `GET /v1/spaces/:id/blobs/:blobId` | `{url, expiresAt}`, a signed GET valid for 15 minutes |

- The GCS object path is `<spaceId>/<blobId>`.
- **`ifGenerationMatch: true`** (current clients always send it): the signed PUT also requires `x-goog-if-generation-match: 0`, which is in `headers`, so the URL can create the object but never overwrite one.
- Asking again for your own pending blob (same size) returns a fresh URL. Once an item references the blob, no URL is issued again: `409 conflict`.
- A blob no item references 24 hours after registration may be garbage-collected.
- In a group, registering a blob needs [Send](#member-access): `403 send_not_allowed` otherwise.

### Constructions

```

AK to a new device   wrapTo(devPub, AK, "c2/device/v1/" + requestId, "c2/device/v1/" + uid + "/" + requestId)
number               10 + (u32be(SHA-256(utf8("c2/number/v1") ‖ utf8(requestId) ‖ devPub)[0..4]) mod 90)
recovery shares      AK = s₁ ⊕ … ⊕ sₙ (sᵢ random for i < n); 1 contact: n = 2, 2 contacts: n = 3, the last is the server's

share to new device  wrapTo(devPub, sᵢ, "c2/recdev/v1/" + recoveryId, "c2/recdev/v1/" + recoveryId + "/" + (contactUid | "server"))

```

`devPub` is the new device's P-256 key (X9.63). `requestId` is the device request's or recovery's id

### Emails

- The server stores `HMAC-SHA256(indexKey, email)` (unique, for lookups) and `AEAD(encKey, email)`;

- `windowMs` 15 minutes to 365 days, or `null` for indefinitely, which needs `acknowledgement` to be

- The server refuses the token after the window (`401 unauthenticated`) and deletes expired sessions.
- The client wipes its keys, sync state and synced data when the window ends or on `401` for a
  device session.

## What the server sees

**Visible to the server:**
- username; the email as an HMAC and as ciphertext under keys outside the database (and briefly in memory, to send mail)
- device names, platforms, approximate location of sign-in requests, and session windows
- recovery setups: who the contacts are, their wrapped shares, and the server's own (encrypted) share
- the scrypt of `authKey`
- KDF salt and iterations
- session hashes, device names and last use
- group membership, roles and member access, and who is whose contact (including pending requests)
- who an authenticator is shared with, each batch's size, `codesUntil` and upload time
- invite ids and expiry
- sign-up code hashes, who made and used each, and expiry
- for about two minutes, auth attempt counts keyed by an HMAC of the IP or email
- per item: category, `sortAt`, `updatedAt`, size, author, blob ids and sizes

Request logs record method, URL and status only: no IPs or emails. Members see each other's
username or email local part (`name`), never the email.

**Never visible to the server:** the password, `wrapKey`, invite codes, item contents, group names, snippet and secret names and values, origins' names, sites, notes and documents, and every key except public keys. With passwordless accounts: `AK` and every recovery share except the server's own (which alone reveals nothing). The email recovery code passes through once, to be mailed.

## Client sync rules

1. **State.** A local *sync meta* table holds `(localId, spaceId, category, fingerprint, remoteSeq, updatedAt)`. `fingerprint` is the SHA-256 of the canonical payload JSON last sent or received. Each space also has a `since` cursor.
2. **Tick.** Triggered 3 s after a local store change (debounced), when the panel opens, on "Sync now", and when [`GET /v1/heads`](#heads) shows a change (polled every 2–10 s; at least every 5 minutes regardless). Against a server without heads, every 3/15/60 s (panel open / active / idle). One tick at a time.
   1. Call `GET /v1/spaces` and unwrap any new space keys.
   2. For each space, pull before pushing.
3. **Pull.** Page through `changes` and apply each item:
   - **Newer upsert:** decrypt. For a clip with images, download and decrypt the blobs and write them to the blob store **before** inserting or updating the item.
   - **`user` tombstone:** delete locally.
   - **`trimmed` tombstone:** in the personal space, stop tracking the item but keep the local copy. In a group, delete it locally.
   - Store the fingerprint and `remoteSeq`, then advance `since`.
4. **Push.** Compare the local items of each space against the meta table:
   - **New or changed fingerprint:** encrypt and `PUT`. Upload new blobs first.
   - **Meta without a local item:** `DELETE`.
   - **On `409`:** apply `current` the same way as a pull.
   - **Personal history:** push only the newest 200 by `lastCopiedAt`.
5. **Duplicates.** When two items in one space share a `contentHash`, the lexicographically smaller id wins. Merge `copyCount`, keep the larger `lastCopiedAt`, keep the label and pin of either, and delete the loser (which pushes a tombstone).
6. **Local scope.**
   - Dedupe, merge and "remove history copies of saved secrets" each run within one space only.
   - Groups locally keep the newest 200 history items per space.
   - The user's own retention setting applies only to the personal space.
7. **Log out** calls `/v1/auth/logout` and then deletes local group data, sync meta, cursors and stored keys. Personal local history stays.
8. **Share to group** copies the item into the group's space with a new id. The hotkey (⌘⌥C / Ctrl+Alt+C, configurable, active only while signed in) copies the current selection and stores it directly in the default group as history.
